## 已确认的原因

### 1. 搜索服务原始响应持续偏题，精确上游机制仍未确定

本次 SearXNG 对正确的空间转录组查询，返回了法国新闻、旅游、公司新闻等无关结果；该 JSON 标注后端 bing、无 unresponsive_engines。最早的原始响应及查询词已保存，说明不是生成模型编造了这些搜索标题。

绕过 LDR/SearXNG，直接请求 Bing，也能得到搜索框回显正确、正文结果偏题的页面；新会话及 no-cache 请求仍重现，TLS 校验正常。另测 2081 路径也有偏题，直连则返回零结果。因此不能简单认定“只要把 9876 换成 2081 就能解决”，也没有证据将原因归为 LDR 重用旧报告或其引用重排。

边界已经定位到 Bing 搜索响应这一层；Bing 内部为什么在这些访问条件下给出错误主题，仍未查明。本地 relay 的代码只转发 TCP 字节，本轮没有修改它。

### 2. 来源池容量与去重反馈，让“有结果”表现成“No results”

本次 121 批收集器输入共 1665 条候选（含重复），只有最早 80 个通过常规搜索新增；114 批非空输入最终返回空列表。该数字混合了去重、容量等原因，不能全部归因于上限。

已直接用 5002 安装版代码、在不联网的独立 Python 进程复现：

| 输入情况 | 返回给工具 | 池中状态 |
|---|---|---|
| 空池加入一篇论文 | 1 条 | 论文已保存 |
| 再次搜索同一论文 | 0 条 | 原论文仍保存 |
| 先有 80 条无关记录，再搜索这篇论文 | 0 条 | 论文未加入 |
| 通过 fetch 注册同一论文 | 编号 81 | 论文被加入，池增至 81 |

这里既有先到先得导致的证据选择问题，也有工具反馈不区分“未命中、已见、未纳入”的问题。

这次初稿声称所有搜索都没有结果、所有 fetch 都失败，但日志实际上有明确返回的 PubMed 条目和成功页面抓取。最终写作收到 108 个来源后又形成了有限综述。不能把初稿的“检索全失败”当作真实执行结果。

**需要修正上次的泛化判断：这次没有用尽 50 轮，也没有触发前 20 个来源的兜底。上次兜底是那一轮拒答的直接触发点，不能解释这次所有失败。** 两轮共有的问题是偏题结果、来源选择/反馈和材料传递；本次也暴露了模型对执行状态的错误概括。

### 3. 本次起初没有摘要，确有 HTTP 限流与不完整降级处理的证据

最初纳入的 36 个 PubMed 来源都没有 abstract/full_content 字段。对应的两批调用分别为：

| 批次 | 预览摘要请求 | 内容摘要请求 | 元数据请求 |
|---|---|---|---|
| 原编号 45–64 | 23.685 秒，429 | 27.199 秒，429 | 29.101 秒，200 |
| 原编号 65–80 | 25.928 秒，429 | 29.091 秒，429 | 32.474 秒，200 |

429 响应明确为 `API rate limit exceeded`。随后成功的元数据 EFetch XML 其实含有摘要，但 `_get_article_detailed_metadata()` 只取元数据，没有将摘要补回。于是“成功取得含摘要的响应”和“来源中没有摘要”同时发生。

本轮开启了 balanced 自适应限流；但 programmatic 模式为各新引擎建立内存追踪器，多个主/子研究同时请求，没有可靠协调同一出口的总体频率。NCBI 的无 API key 限制按 IP 计算，通常每秒最多 3 次，见[官方说明](https://www.ncbi.nlm.nih.gov/books/NBK25497/?report=printable)。所以不能只给每个独立工具一个短等待，就认为整个研究已满足服务端限制；这也受共享出口其他请求影响。这里的 429 计数是本次运行观察，不等同于网页账号路径的固定表现。

随后部分重复检索补回了摘要。最终 36 个 PubMed 来源中，13 个有摘要、23 个仍无摘要字段。原编号 54 在 37.426 秒输入了 2428 字符摘要，但该批返回数量为 0；收集器合并了材料，却没有把更新后的来源返回给 Agent。这解释了为什么 Agent 会持续看到空结果，而最终综合又能拿到一些新内容。

### 4. XML 解析和页面注册造成第二类材料损失

将本次成功返回的一批真实 XML 固定下来，替换 HTTP 为离线响应，再调用 **5002 原有 `_get_article_abstracts()`**，仍能复现问题。例如 PMID 42882098 原 XML 有 2453 字符摘要，安装版解析器返回时却完全没有该记录。原因是仅取 `.text`，忽略内嵌标签及其后续文字；另有首段重复拼接。

这个离线回放与 HTTP 429 无关，证明“请求失败”和“请求成功后解析丢失”必须分别修复。

最终 28 个 fetch 来源全部没有保留 full_content，snippet 均不超过 203 字符；其中 23 个是 PubMed 搜索结果页。它们是发现线索，不能当作已取得单篇论文 Methods 的证据。抓取工具本身还限制前 10000 字符；取得一段 PMC 页面不等于读全论文。

### 5. 书目信息已经在系统里，却没交给最终模型

最清楚的实例是原编号 54、最终展示编号 7：

| 字段 | 来源字典中已有 | 最终写作实际提示词 |
|---|---|---|
| 标题 | Spatial transcriptomics unveils the in situ cellular and molecular hallmarks of the lung in fatal COVID-19. | 没有该标题 |
| 期刊 | Nature communications | 没有统一传入该字段 |
| 日期 | 2026 Oct 15 | 没有统一传入该字段 |
| DOI | 10.1038/s41467-026-78188-3 | 没有该 DOI |
| PMID | 42881179 | 没有该 PMID |

旧 `_create_documents()` 优先取 full_content，而 `_format_sources()` 只输出编号及文本，没有系统地附上结构化书目头。这个来源变成了一段重复的摘要及其他元数据，关键身份字段没有进入提示词。

最终逐篇证据表因此写“未提供明确标题”“期刊未明确”“DOI未提供”。同时最终书目又能显示完整标题，因为书目走的是来源字典。这个前后矛盾有明确的代码与输入证据，不能简单归为模型忘记了标题。

### 6. 最终写作还存在纳入条件与证据对应错误

本次输出虽然比上次丰富，但仍有可明确指出的问题：

- 输入明确允许实际分析目标平台数据的方法学/基准研究；输出却把多篇 benchmark 以“方法学，非原始应用研究”为由排除，改变了纳入标准。
- 共用分析表用 GeoMx DSP 研究支撑差异表达，而本题限定的平台没有 GeoMx；后文又将该研究列为不符合平台条件，前后不一致。
- 没有完成逐刊 JIF 数值、年度、来源核实，却仍使用“公认”“可合理推断”等表述。
- 将摘要或模型内部训练步骤概括为通用分析模块，未逐项建立“哪篇目标研究实际执行了哪一步”的证据对应。表格看起来完整，实际提取的 Methods 依据不足。

独立复核了本轮已搜到书目信息的 [2025 年 Nature Communications 平台基准研究](https://www.nature.com/articles/s41467-025-64292-3)：论文确实生成并分析了 Stereo-seq、Visium HD、Xenium 等数据。报告却把它以基准研究为由移出主要候选，同时称没有相应平台研究。其 JIF 仍须按任务口径另核，但至少不能仅因 benchmark 这一类别排除。此次独立核查未作为材料反馈给运行中的 Agent。

### 7. 范围引用重排漏洞再次出现在真实输出

新报告保留 `[1-7]`、`[8-17]`、`[18-27]`、`[28-37]`、`[38-44]` 五个旧编号范围；它们未被解析或重排。

最直接的表现是：正文开头将 `[1-7]` 描述为法国新闻，但最终展示编号 7 已经是上述 Nature Communications 的 Visium 肺组织研究。可识别单号仍正确映射到原来源；范围引用则残留了原编号体系，造成同一报告内的语义错配。

`[45]-[108]` 这种范围表述也被当成两个单号，变为 `[1]-[2]`。应统一处理范围语法，再让正文、审计、书目和导出使用同一映射，而非只补某一个正则出口。

## 调整顺序

1. 检查搜索响应相关性，修复当前 Bing 路径异常；避免无关网页未经相关性处理占满来源池。不能凭一个替代代理的单次成功就切换运行配置。
2. 明确候选、重复更新、容量未纳入及真正零命中的工具反馈；按相关性与平台覆盖选择材料，修复前 20 个来源的兜底选材。
3. 对 NCBI 做共享节流、适当重试及批量 XML 复用；成功 XML 同时解析摘要与元数据，避免反复获取同一记录后又丢弃已取得的信息。
4. 保留实际取得的原文与章节定位，修 XML 与短摘要注册；写作输入明确附标题、期刊、日期、DOI/PMID、证据范围。
5. 先建立逐论文分析证据条目，再综合平台共性；显式保留本题纳入条件，避免表格覆盖感替代真实证据。补统一范围引用解析。

这些是已完成诊断后提出的调整，本轮没有部署修复。此前未上线的 grounding 补丁覆盖部分材料保存、XML 和提示词问题，但没有完成这里的全部修复；本次也不是补丁前后准确率对照。
