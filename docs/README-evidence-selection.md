# DRA 文献检索与证据核查的开放问题

截至 2026-11-24，以下问题来自隔离候选镜像 `astro-dra:coverage-e2e-final-kyynzo` 的实测。采集这两轮记录时，5006 线上运行 `astro-dra:evidence-selection-v14-5006`。本页以候选版为准，已修复项及其验证记录见[开发记录](development-progress.md)。各项“策略”均待实现或验证。

| --- | --- |
| 第 6 条「10X Xenium 发表了哪些文献？」 | 首轮从检索开始，用时 27 分 20 秒，初稿截断。复用同一批 14 条来源调高输出上限，重跑写作至报告输出，用时 25 分 22 秒。 |
| 第 2 条「真核 RNA 质检在 18S、28S 之外出现低峰，是否建议继续测序？」 | 从检索到成稿用时 60 分 08 秒，收集 9 条来源，引用 5 条。检索约占 27 分钟。 |

两次实测后，候选镜像 `astro-dra:citation-range-recovery` 修复了发布时引用区间改号以及模型输出截断后的恢复。下列开放问题按对用户决策与检索交付的影响排列。修复的验收范围见[开发记录](development-progress.md)。

## 1. 核查发现证据不足，最醒目的建议仍然偏强

**现象与根因。** RNA 报告承认现有材料无法判定杂峰身份、污染阈值或该样本是否符合放行条件，首段仍给出“通常可以继续测序”的条件性建议。覆盖核查把核心问题判为部分回答。补查模型返回空请求后，现有分支直接返回原文。这能保留缺口记录，却没有让 writer 重新检查首段措辞与证据是否相称。[补查决策](../local_deep_research/research_verify/task_evidence.py) · [返回原文的分支](../local_deep_research/research_verify/evidence_flow.py)

**这次 RNA 运行的直接记录。** 检索交给 writer 的草稿为空。写作指令要求先回答决策，并在缺少阈值时提出可验证的条件性下一步。writer 在初稿中自行写出“通常可以继续测序”。包含首段的 8 条论断首次核查与重试分别在 16,384 和 12,000 token 处截断。后续覆盖核查识别了证据缺口，补查返回空列表，成稿正文与初稿哈希一致。归档保存了写作提示、可见答复和核查轨迹；本次无账号测试入口未接入独立的原始响应采集器。

**策略与验收。** 把已确认的证据、未确认的前提和原句一起交回 writer，由它判断原句是否会让读者误以为已有足够依据。合理的修改可以只收窄结论，无需新增事实；若新增事实，继续核对来源。允许停止补查，避免把核查备注机械追加到正文。回放本例时，首段应让读者直接看出这些材料尚不能决定这份样本能否继续测序。换成有直接证据的任务时，报告应保留证据支持的明确结论。

## 2. 检索多轮找到了相关词，却没有找到能回答决策的研究

**现象与原因边界。** RNA 题多次查询零命中，候选池里出现原油降解菌研究。最终引用的材料能解释宿主和细菌 RNA 混合等背景，未直接评估用户描述的质检情形。运行记录能确认，多轮检索后核心问题仍缺证，流程随后进入写作；仅凭本轮不能断定原因来自某个搜索引擎、查询生成或排序。

**策略与验收。** 让智能体在规划下一次查询前先回答“上轮新材料解决了哪个问题，还差什么”。连续得到间接材料时，可改换来源、换一种研究设计或方法描述来搜索，也可解释继续搜索的收益有限。保存查询、命中、入选理由及证据用途，区分问题出在没搜到还是搜到后没选中。用不同主题的决策题回放，比较首次取得直接证据的时间、重复空查询和最终结论的依据。

## 3. 抓到目录页，仍取不到可核对的文献条目

**现象与原因边界。** Xenium 成稿引用了三个官网目录地址。页面片段显示 `0 Results`，没有可核对的条目；补查时还有官网请求返回 HTTP 429、Europe PMC 请求返回 403 的记录。现有材料只能确定此次读取的内容，无法据此判断官网真实收录量，也无法确认首轮空片段是否由动态渲染导致。成稿已说明这项限制。

**策略与验收。** 让读取步骤分别记录访问结果、读到的条目和可确认的覆盖范围。目录内容不足时，让智能体按用户目的选择分页、其他公开入口或独立文献索引，并记录每条例子的出处。用空页面片段、拒绝访问、有可读条目的分页目录三种输入回放，验证前两种不会产生“共零篇”的结论，第三种可以交付实际读到的条目。

## 4. 核查把开放式提问扩大成了穷尽性任务

**现象与根因。** 用户问“发表了哪些文献”。Xenium 补跑中，核查模型自行把“全部文献清单”和“专门论文数量”列为问题，并为全量清单发起补查。原话允许列举，也可能表达全面检索的意图，但没有明确要求精确总数。现有流程允许模型提出核查问题并据此补查，这次把模型自己的范围推断也当成了交付缺口。[范围生成与补查](../local_deep_research/research_verify/task_evidence.py)

**策略与验收。** 核查时让模型说明每项范围判断依据哪句用户原话。意图开放时，先核实实际列出的文献，交代检索边界；用户明确要系统清单或总数时，再核对检索覆盖和去重依据。以“举几个例子”“有哪些”“尽量列全并统计”及其改写做对照，观察补查目标是否随含义变化，避免用词表硬判。
